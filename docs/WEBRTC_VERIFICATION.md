# Проверка видеозвонков — 27 сентября 2026

## Причины нестабильности

- Полноэкранная и встроенная комнаты имели отдельные реализации WebRTC. Полноэкранная комната смешивала Socket.IO с HTTP/SSE-сигналами и разными идентификаторами участников. Устаревшие и дублирующиеся события могли попасть в новый peer connection.
- Создание offer, установка remote description и обработка ICE выполнялись конкурирующими асинхронными обработчиками. Ранний ICE, одновременные offers и повторный вход не были надёжно изолированы.
- Жизненный цикл медиапотоков и соединения расходился: поздно завершившийся getUserMedia, переключение камеры/экрана и размонтирование могли оставить старые треки или потерять отправителя видео.
- Приём звонка ожидал HTTP-запрос, который, в свою очередь, ожидал внешний сервис уведомлений без таймаута.
- Конфигурация содержала localhost для Socket.IO и не содержала рабочего TURN. localhost на другом устройстве указывает на это устройство; STUN не заменяет TURN в сетях, где прямое соединение невозможно.

## Исправления

Один контроллер WebRTC используется обоими интерфейсами. В нём — очередь SDP/ICE, perfect negotiation с polite rollback, фильтрация ICE по поколению, отдельный sessionId каждого входа, закрытие старого соединения, ICE restart и ограниченные повторные попытки входа. Сервер проверяет комнату, реальный socket отправителя и сессии обеих сторон. Третий участник не заменяет активного собеседника.

Камера, микрофон и экран имеют единый cleanup. Поздние результаты захвата останавливаются после выхода. Фиксированные аудио/видеотрансиверы позволяют включить камеру после аудиовхода и заменить видео демонстрацией экрана. Демонстрация не скрывается при выключенной камере.

Звук воспроизводится одним audio-элементом независимо от мобильного/desktop layout. При блокировке autoplay показывается кнопка включения звука. Приём/отклонение звонка больше не ждут HTTP-уведомления; внешние публикации уведомлений ограничены таймаутом. Повторные приглашения для уже принятой комнаты игнорируются.

Сохранены существующие страницы, внешний вид, authentication, API выполнения кода и Socket.IO. Для совместного редактора сохранены предыдущие правки: серверный snapshot, локальный cache, ревизии; добавлены защита от устаревших ACK и фильтрация событий по комнате. Это не CRDT: одновременное конфликтующее редактирование и восстановление после перезапуска сервера требуют отдельной проверки/доработки.

## Что ещё необходимо для публичного сайта

1. Запускать постоянный Socket.IO-сервер через `node server.js`, а не только `next start` или serverless Next.js. Для отдельного backend задать публичный HTTPS-адрес `NEXT_PUBLIC_SOCKET_URL`; для общего сервера оставить переменную пустой. Оба участника должны попадать в один серверный процесс: распределённые signaling/room-state в этой правке не реализованы.
2. Для настоящих устройств нужен HTTPS; HTTP localhost подходит только устройству, на котором открыт браузер. Телефон по HTTP LAN-адресу может не получить доступ к камере/микрофону.
3. Указать рабочие `NEXT_PUBLIC_TURN_URLS`, `NEXT_PUBLIC_TURN_USERNAME`, `NEXT_PUBLIC_TURN_CREDENTIAL`, затем пересобрать приложение. Пример есть в `.env.example`. Эти NEXT_PUBLIC-значения видимы браузеру: не использовать административный пароль TURN; для production предпочтительны короткоживущие клиентские credentials.
4. Проверить два физических устройства в разных сетях, например Wi-Fi и мобильный интернет, а также Safari/iOS. Дополнительно проверить принудительный relay и статистику выбранной candidate pair: успешный localhost-тест не доказывает доступность TURN.

На этом этапе рабочие TURN credentials не предоставлены. Физические камеры, разные внешние сети, Safari/iOS и production deployment не проверены. Исходники исправлены локально; публикация на GitHub/хостинг этим отчётом не подтверждается.
